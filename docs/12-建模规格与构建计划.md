# 12 · 建模规格（spec）与构建计划（P2）

> 把 P1 收集到的「看图结论」固化成**可校验、可复用、可驱动建模**的结构化数据。
> 状态：已实现 + 17 项单元测试通过；工具待 DSH 重启后接真实调用验证。

---

## 1. 为什么要有 spec 这一层

P1 的产出是一张对照表，看完之后结论在**模型的上下文里**。这有三个问题：

1. **不可复用**：换会话/隔天继续就得重新搜图重新看。
2. **不可校验**：看不出"这个方案大概率会做砸"（比如头部只给了 10% 方块）。
3. **不可驱动**：建模时仍需现场决定"先建什么、每块给多少"。

spec 就是把这些结论**外化成文件**。好处直接对应：

- 错了改 spec，不用重跑搜索/看图
- 可被规则校验（规则来自语料实测，不是拍脑袋）
- 可直接推导出构建计划，喂给 `bb_apply_model_patch`
- 可人工审阅——比审一张生成图靠谱

---

## 2. spec 结构

```jsonc
{
  "spec": "ysm-model-spec/1",
  "character": { "name": "角色名", "source": "出处" },
  "references": {
    "dir": "refs/<角色>",
    "images": [ { "index": 0, "angle": "front|side|back|three_quarter", "kind": "sheet|fullbody|screenshot|fanart", "note": "" } ]
  },
  "palette": [ { "name": "hair", "hex": "#a8b8d8", "usage": "头发" } ],
  "parts": [
    { "id": "hair", "bone": "Hair", "cubes": 90, "shape": "披肩双马尾+丝带",
      "colors": ["hair"], "refs": [0, 2] }
  ],
  "budget": { "cubesTotal": 306, "textureSize": 512 },
  "gaps": ["缺背面参考图，裙后摆按对称推测"],
  "notes": ""
}
```

---

## 3. 校验规则（有出处，不是主观设定）

| 规则 | 等级 | 依据 |
|---|---|---|
| `character.name` 必填 | error | — |
| `parts` 非空 | error | — |
| 每个部位有 `id` / `bone` / `cubes>0` | error | — |
| 部位 `id` 不重复 | error | — |
| `palette[].hex` 必须是 `#RRGGBB(AA)` | error | — |
| 部位引用未定义的色号 | warning | 允许先写后补 |
| **缺背面参考但 `gaps` 未记录** | **error** | 产品决策：必须显式告知用户 |
| 缺侧面参考 | warning | 厚度只能推测 |
| 方块总数 `< 60` 或 `> 600` | warning | 语料人物 50–300，雕刻派到 600 |
| 与 `budget.cubesTotal` 偏离 >40% | warning | — |
| 头部占比不在 28%–48% | warning | 语料中位 33.2%，成品感主要来自头 |
| `textureSize < 256` | warning | 语料 512 占 35%，128 只占 21.5% |

**`gaps` 那条是唯一"故意做成 error"的**：网上背面图极稀缺（实测 16 张里 1 张），
既然策略是"继续做、背面靠猜"，就必须留下痕迹，否则最后交付时用户不知道哪里是猜的。

## 4. 构建计划（derivePlan）

spec → plan 做三件事：

1. **排序**：`torso → leg → arm → head → hair → skirt → accessory`（先大形体，后细节）。
2. **父子骨骼**：按 YSM 标准骨架映射（`Head→AllHead`、`Hair→Head`、`Skirt→DownBody`…）。
3. **贴图分区**：按各区域方块数占比分配面积，给出每个区域的目标像素数。

输出：

```jsonc
{
  "order": ["torso","leg","arm","head","hair"],
  "bones": [ { "part":"hair", "bone":"Hair", "parent":"Head", "cubes":90, "region":"hair", "colors":["hair"], "shape":"...", "refs":[0,2] } ],
  "texture": { "size":512, "regions":[ {"region":"hair","share":0.38,"areaPx":99532} ] },
  "totals": { "cubes":240, "headShare":0.43, "parts":6 }
}
```

建模时按 `order` 走，每个 `bone` 按 `cubes` 做预算 —— 这就是"按清单搭"而不是"凭感觉堆"。

---

## 5. 工具

| 工具 | 作用 |
|---|---|
| `bb_spec_save({spec})` | 校验 → 落盘 `specs/<name>.json` + `.md` → 返回 plan |
| `bb_spec_load({name?})` | 读回 + 重新校验 + 返回 spec/plan/markdown；不传 name 列出全部 |

都不依赖 BAE（纯文件操作），所以**Blockbench 没启动也能用**。

---

## 6. 与 P1/P3/P4 的衔接

```
P1 bb_ref_search / bb_ref_collect   → 对照表（模型看图判读）
        ↓ 模型写 spec
P2 bb_spec_save                     → specs/*.json + plan
        ↓ 按 plan 调用
P4 bb_apply_model_patch / bb_look   → 建模与自检（和参考图对账）
```

P3（See-through 分层）接入点：分层结果可以丰富 `references`（每层对应一个部件的参考），
并作为 `parts` 的独立依据。spec 结构不用改。

---

## 7. 未做（有意）

- **不做自动生成 spec**：spec 的核心价值是"模型判断过、可审阅"。自动生成就退化成黑箱。
- **不做 spec → 直接建模的一键流水线**：中间要有人/模型确认，否则错误会放大。
- **不做 spec 的版本 diff**：目前一份 spec 对应一次建模；要迭代就重存。
