## 2. 方法与脚本

```bash
python tools/mine_corpus.py    # 解析 -> 材料/_dataset.json（逐模型结构特征）
python tools/mine_deep.py      # 骨架层级 / 部位配额 / Locator / 贴图规格
python tools/mine_profile.py   # 竖向分布 / 头部占比 / 贴图尺寸
```

`mine_corpus.py` 把两种格式归一化成同一 schema：
`bone_count / cube_count / bone_names / parents / cubes_per_bone / height / uv_modes`。

`mine_profile.py` 换成**按世界 Y 坐标分段**统计，绕开 `.bbmodel` 里大量
`bone/bone2/boneN` 自动命名导致的归类失效。

## 3. 关键发现

### 3.1 方块预算与竖向分布（114 个模型 / 44,072 方块）

| 区段 | Y | 占比 |
|---|---|---|
| 脚 | 0–3 | 4.6% |
| 小腿 | 3–12 | 11.1% |
| 大腿 | 12–21 | 17.6% |
| 臀腰 | 21–25 | 10.9% |
| 躯干 | 25–32 | 17.0% |
| **颈/头/脸/发** | **32–40** | **19.8%** |
| **头顶以上（呆毛/头饰）** | **40+** | **18.2%** |

- 方块总数中位 **306**（四分位 153 / 503）；方块/骨骼 **4.9**。
- **头部区域（Y≥32）占 33.2%（中位）**，即三分之一方块在头上 → **成品感主要来自头部**。

### 3.2 贴图尺寸（223 张）

| 边长 | 占比 |
|---|---|
| **512** | **35.0%** |
| 128 | 21.5% |
| 256 | 19.3% |
| 64 | 9.9% |
| 32 | 7.6% |
| 1024+ | 2.2% |

→ **128 只是默认模板遗留，不是行业标准**。本项目此前一直用 128，导致眼睛仅 2×2 像素。

### 3.3 骨架层级（181 个模型）

高频父子边：`AllBody→UpBody`(54%)、`Arm→RightArm`(54%)、`RightHand→RightHandLocator`(54%)、
`AllBody→DownBody`(54%)、`DownBody→LeftLeg`(41%)、`AllHead→Head`(41%)。
层级深度中位 **10–11 层**。

### 3.4 Locator

`RightHandLocator` / `LeftHandLocator` 各 **62%**；其余（Elytra/Rifle/Pistol/View/Waist）
均在 7% 以下 → **手部挂点必加，其余按需**。

### 3.5 UV 模式

资源包 `main.json`：box 38% / per-face 62%；`.bbmodel`：box 100%。
→ 成品包多改 per-face 以精确控制贴图区域。

## 4. 纠错记录（本次最大收获）

**曾把"默认模板 64 bones / 172 cubes"当成"YSM 上限"，并据此砍掉了该加的 Locator。**

- 该错误陈述写在 `skills/blockbench-ysm-artist.md` §8 与 `sakiko-final/README.md` §5，
  两处均已更正。
- 证据：语料 **77% 的模型 >64 骨**，中位 83，最高 **451**（`augusto_pinochet_helicopter`）。
- 真实约束（官方文档）：
  - 骨骼**嵌套层数** ≤ 32（YSM 2.6.3 起解除），不是骨骼数量；
  - 贴图分辨率上限 **4096×4096**（2.2.2 起）；
  - 模型包体积 2 MB 限制已在 1.2.0 取消。

**教训**：任何"上限/限制"的说法，先去语料里找反例。找到反例就是判断错了。
这条已写成语料规则 §0，作为技能的第一节。
