# 11 · 参考图收集管线（P1）

> 目标：建模前先「看见角色」。不依赖任何生成式三视图服务，改用**互联网多源搜索 + 多模态判读**，
> 零安装、可分发（插件要给别人用）。
>
> 状态：**已实现并实测通过**（丰川祥子，见 §6）。

---

## 1. 为什么不用「AI 生成三视图」

| 方案 | 问题 |
|---|---|
| 专用 LoRA（CharacterSheet 等） | 要装 ComfyUI + SDXL，一致性靠调参，二次元角色易漂移 |
| 图像编辑大模型 | 按次计费，背面靠脑补，配饰/发型背面经常崩 |
| ControlNet + OpenPose | 2023 年玩法，二次元骨架提取不准，投入产出比最差 |
| Adobe Turntable | 只吃矢量插画，输出矢量，与位图立绘无关 |

**根本原因**：三视图最难的不是"画出来"，而是"换个角度还是同一个角色"。
而互联网上**本来就存在**官方设定集、多角度立绘、动画截图——直接搜集比生成更可靠、更便宜。

---

## 2. 架构（为什么切成三段）

```
bb_ref_search(character)     多源搜索 → 候选 URL 列表（按信息密度先验排序）
        ↓
bb_ref_collect(urls?)        下载 + 格式校验 + 精确/感知去重 + 拼对照表（一张图）
        ↓
（模型看图判读）              同一角色？各是什么角度？哪些是设定集？
```

**拆三段而不是端到端**的关键理由：中间的「看一眼」必须能介入。
搜索结果质量参差，黑箱拼完直接进建模会把错误带进去；对照表出来后人/模型先筛一遍，成本最低。

---

## 3. 源策略（实测可达性）

| 源 | 接口 | 实测 | 说明 |
|---|---|---|---|
| **bing** | `www.bing.com/images/async` | ✅ 34 条/查询 | 主力。初始 HTML 是异步加载的，必须打 async 接口 |
| **so360** | `image.so.com/j` | ✅ 30 条/查询 | JSON，返回 `list[].img` |
| **moegirl** | `commons.moegirl.org.cn/api.php` | ✅ | MediaWiki，官方图多；分类命中率高于全文 |
| baidu / sogou / yandex | — | ❌ | 反爬页（返回 1–9 KB） |
| duckduckgo | `i.js` | ❌ | vqd 流程已变，取不到 token |
| danbooru / konachan / zerochan | — | ❌ | 403 / 503 / 超时（国内网络） |
| pixiv | — | ⚠️ | 页面可达，图片需登录/referer |

**设计约束**：单源失败只记录状态、不抛错。站点会封会改版，硬编码单源必死。
`bb_ref_search` 返回 `sources[]`，每个源有 `ok / count / error`，**不许谎报成功**。

## 4. 排序：按「信息密度」而不是相似度

```js
priorScore = kind(sheet:+40 | fullbody:+25 | back:+20)
           + 竖图(+12) + 高清(+8) - 小图(-20)
           + 官方域名(moegirl/fandom/wiki:+15)
           - avatar/icon/logo(-25)
```

**为什么这样排**：建模要的是「结构信息」，不是「画得好看」。
一张设定集扫描页（含正/侧/背 + 线稿）价值 > 十张同人立绘，且一致性 100%。

---

## 5. 下载与去重

- **格式校验**：按魔数判断 PNG/JPEG/WebP/GIF/BMP，不信 content-type 与扩展名
- **尺寸**：从头部字节解析宽高（PNG IHDR / JPEG SOFn / WebP VP8X|VP8|VP8L），无解码库
- **精确去重**：sha256
- **感知去重**：bridge 侧 canvas 缩到 9×8 算 **dHash**，汉明距离 ≤6 视为同一张图
- **URL 归一化**：非 ASCII 百分号编码。**Node fetch 对原始 CJK 会抛 ByteString 错误**（实测百度图床必踩）
- **Referer 提示表**：hdslb→bilibili、bcebos→baidu、dtstatic→duitang 等；不带就 403

**为什么拼版放 bridge**：host 侧没有原生图像库（`nativeImage` 不可用，实测），
只有 renderer（BAE）有 canvas 能解码。所以 `ref.sheet` 在 bridge，逐张 `load → draw → hash → 丢引用`，
避免 24 张 4000px 原图同时驻留内存。

## 6. 实测（丰川祥子 / 2026-11）

| 指标 | 结果 |
|---|---|
| 查询数 | 5（`丰川祥子` / `设定集` / `三视图` / `全身立绘` / `背面`） |
| 候选 | **129** 条（bing 99 + moegirl 17 + so360 13） |
| 下载 | 36 尝试 → **16 成功**（约 44%；失败主因是 403 与超时） |
| 拼版 | 1024×818，16 格，**936 KB**，约 900 token |
| dHash | 16/16 成功，本轮无重复组 |
| 同角色判读 | **16/16 全是同一角色**（浅蓝发、琥珀瞳） |
| 角度覆盖 | 正面多、侧面少、**背面仅 1 张（且来自设定集）** |

**实测图像来源分布**：官方立绘/设定集 3 张、动画截图 7 张、同人 10 张、Q版/群像 2 张。
→ 约 40% 是低价值素材，**筛选比搜索更重要**。

## 7. 已知限制

1. **背面极稀缺**：这是互联网内容的客观分布，不是实现问题。
   按既定策略：**凑不齐继续做，背面靠推测，最后明确告诉用户"缺背面参考"**。
2. **比例漂移**：同人图之间比例差异可达 10–20%，不能直接量尺寸。
   只取"结构有无"和"配色"，比例以官方设定集/立绘为准。
3. **站点不稳定**：源会封。加源只需往 `SOURCES` push 一个 `{id,label,search}`。
4. **不含分类能力**：多模态打标由模型（agent）看图完成，插件只负责取图与拼版。
   这是有意为之——避免把"判断"变成黑箱。
