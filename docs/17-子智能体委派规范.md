# 17 · 子智能体委派规范（强制）

> 决定：**`bb_*` 插件的所有实质性调用，都必须由子智能体执行。**
> 主代理只负责「理解请求 → 完善任务书 → 拉起子智能体 → 验收汇总」。

---

## 1. 为什么必须这样

这不是流程洁癖，是四类真实事故的防线：

| 问题 | 不委派会发生什么 | 实际证据 |
|---|---|---|
| **图像 token 污染** | 每次渲染 200–900 token；一轮建模几十次看图就能把主会话塞满，后续推理质量下降 | 本项目主会话一度被渲染图占满 |
| **跳过前置步骤** | 主代理容易「看到请求就改方块」，漏掉搜参考图 / 写 spec / 看对照表 | 早期版本曾凭记忆建模，角色发色瞳色全错 |
| **长任务被打断** | 建模动辄 20+ 次写操作、多轮看图、下载几 GB 权重 | T2 首次要下 12.5GB，主会话阻塞不可接受 |
| **事故无法隔离** | 一次误删/误涂直接污染主线状态，无法干净重来 | 实测 `delete` 静默失效曾让错误状态被继承 |

子智能体有独立上下文，图只进它的窗口；失败可以直接重开一个，不污染主线。

---

## 2. 流程

```
用户请求
   ↓
主代理：判定任务类型，不碰 bb_*
   ↓
主代理：按 assets/delegation-brief.md 填任务书
   ↓
子智能体拉起（context=fresh 优先）
   ↓
子智能体 Step 0「promote」：补全任务书 → 输出可执行计划 → 指出矛盾/缺失
   ↓
子智能体执行：参考 → spec → 建模 → 贴图 → 自检 → 动画 → 导出
   ↓
子智能体回报：产物 + 实测 + 偏差 + 未做 + 问题
   ↓
主代理：验收（抽查产物、核对数字）→ 汇总给用户
```

---

## 3. promote（完善任务书）是硬要求

子智能体的**第一个动作**不是调工具，而是把主代理给的任务书补完：

- 空缺字段填上默认值并说明依据
- 矛盾项当场指出（例如「要求精修但预算只给 10 次渲染」）
- 输出一份可执行计划（目标 / 角色 / 服装 / 部件 / 预算 / 验收 / 风险）
- 计划里必须包含「我会用哪几张参考图、看什么」

这一步的价值：**把模糊需求变成可验收的合同**，避免执行到一半才发现方向错了。

---

## 4. 主代理的验收职责

子智能体回报后，主代理不能只看它的自述，必须抽查：

| 抽查项 | 怎么做 |
|---|---|
| 产物真的存在 | 列目录、看文件数与大小 |
| 数字对得上 | 报告说 N 骨 M 方块，就用 `bb_scene` / 读 `main.json` 核对 |
| validate 真的 0 error | 重跑 `bb_validate` 或核对导出 manifest |
| 没做的项被诚实标注 | 检查报告里是否有「未做」段，以及原因是否具体 |
| 声称的修复真生效 | 例如它说绕过了某 bug，要看它绕的是工具缺陷还是自己用法错 |

**实测教训**：全新用户验收报告里有一条「`add_cube` 的 uv_size 无法强制」，
核对后发现 `uv_mode:"faces"` 时 `uv_size` 是生效的 —— 是执行者用法问题，不是 bug。
如果不抽查就会去"修"一个不存在的 bug。

---

## 5. 例外

只读、一次性的状态查询可以由主代理直接做：

- `bb_session_status`（看是否连上、预算余量）

一旦涉及**看图**（任何带渲染返回的工具）或**改模型**，就必须委派。
